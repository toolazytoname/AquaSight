# Free BYOK 切换与容量实测

## 已切换

项目统一使用 `https://litellm.weichao.site/v1`、模型 `free`、用户已有 `weichao-personal` token。GitHub Secrets 已更新；token 未写入仓库。原本数据库保存的是该 token 的哈希，服务器 `/opt/litellm/secrets/personal.key` 保存有可复用的原始值，已核验二者一致。

New API 原有 `free → auto`、`free:fast → auto:fast`、`free:smart → auto:smart` 没有改动。读取 LiteLLM 文件配置和模型接口时缺少 free，故只补上 `free → New API`，下游使用原有 AquaSight 免费专用 token，个人 key 增加 free 权限，保留原有 auto 等权限。为本次排查临时创建的 aquasight-free key 已撤销。LiteLLM 配置已备份并重载，健康检查成功；本项目调用不回落到付费路由。

## 实测结果

同一组 8 条真实早报样本，仅使用项目的 enrichment 代码，不手工修改结果。

| 指标 | 第一轮 | 修正校验后复测 |
|---|---:|---:|
| 结构通过 | 7/8 | 8/8 |
| 中文标题 | 7/8 | 8/8 |
| 外层 HTTP 请求数（含重试） | 10 | 10 |
| 总耗时 | 210.4 秒 | 216.6 秒 |
| 报告的输入 token | 3,429 | 3,707 |
| 报告的输出 token | 16,320 | 16,954 |
| 报告的费用 | 0 | 0 |

复测单条耗时约 9–59 秒，平均约 27 秒。8/8 表示本次样本的结构和中文校验通过，不等于长期成功率或独立事实核查通过。免费池动态选择上游，延迟与输出质量会变化；某些上游的 reasoning token 明细甚至大于 completion token，容量测算采用其标准 usage 字段，不再相加。

已修复失败缓存复用、切换模型仍复用旧缓存、成功后残留失败标记；采用 2400 token 输出预算，校验失败有一次较大输出预算重试，临时限流先退避。成功结果继续缓存，新增日输入/输出 token 统计。

早报现在先补齐中文与事实、生成并校验综述，再保存并推送。网页与通知共用准备好的刊期；通知直接进入新域名的早报页。未能完成中文标题的条目不会直接回退成全英文早报。历史已推送刊期不强制重发。

## 免费额度能承担多少

实际查询免费池内 OpenRouter key 接口：`is_free_tier=true`，`free_model_daily_requests={used:12,limit:50,remaining:38}`（本次排查时点）。这比简单统计已配置模型数可靠；50 是该 OpenRouter 账户共享额度，不能按免费模型数相乘。[官方限额说明](https://openrouter.ai/docs/api_reference/limits)。

池内还配置有 Groq、Mistral、OVH 等上游；不能把目录配额或旧 remaining 数相加当成实际余额。比如 Groq 公布的 gpt-oss-120b 免费档有 200K token/日的约束，还同时受 RPM/TPM 限制；账户实额需以服务商接口/控制台为准。[Groq 限额说明](https://console.groq.com/docs/rate-limits)。

按本次样本的约 2,583 token/条（含重试）粗估：

- 10 条早报：约 2.6 万 token，加一次综述；当前样本证明核心整理可运行。
- 30 条精选：约 7.7 万 token；缓存命中会降低实际新增消耗。
- 100 条完整整理：约 25.8 万 token。
- 每天四轮各 100 条全部重新整理：约 103 万 token，不能承诺现有免费池每天稳定承担。

这些是基于标题/摘要样本的估算；生产抓取较长正文、其他应用共享账户、上游重试都会增加用量。结论：核心早报与精选可先用起来，但全量高频深度整理需要持续观察实际路由、缓存命中、失败和 token 用量；不通过强行耗尽额度来证明容量。


## 30 条精选 + 综述的实际负载测试

证据：[30 条测试与单独复测](./free-30-evaluation-2026-09-25.json)。全部请求经外层 LiteLLM，模型始终为 `free`，没有付费模型兜底，没有发送通知。

- 原始批次：并发 2，约 604 秒，30 条新闻加一次综述共 45 次调用（含自动重试），输入 17,792、输出 95,318 token，共 113,110 token。生产流水线仍按原有顺序处理，不能照搬并发测试耗时。
- 新闻首轮含自动重试后：29 条通过旧结构校验，但其中 1 条是照抄模板，人工剔除后实际为 **28/30**。另 1 条 JSON 解析失败。所有被记录的 44 次文章 HTTP 请求均为 200，HTTP 成功不等于内容成功。
- 新增模板拦截、缓存重新校验、重试错误提示后，两条异常样本单独复测均成功。不能据此宣称未来必然 100% 成功。
- 综述第一次被截断；将输出预算由最多 1600 提升至配置值两倍（本次 4800，上限 8000）后复测生成成功，数字/来源启发式检查通过。但写了 8 句，且夹带普通英文词 drafting，仍不满足理想编辑风格；启发式检查不是独立事实核查。
- 服务端观测到 Kilo 与 OpenRouter 都实际承接了请求。自当天 14:00 UTC 起的排查累计统计（包括此前小样本，非单独本批次）：Kilo 成功 26 次，OpenRouter 成功 39 次、错误 1 次。不能把 OpenRouter 的额度当成整个 Free 池额度。
- 批次末段查询 OpenRouter 实时额度为 used=40、limit=50、remaining=10；该时点在最后独立复测完成之前。其他上游余额尚不能可靠汇总。

**判断：已实证纯 Free 能跑本次 30 条精选与综述，适合继续承担每日早报和精选整理；不能承诺每天 400 条的稳定吞吐。当前主要问题是输出一致性和重试开销，不是这轮负载下额度耗尽。** 这批消耗高于之前 8 条样本推算，因此不再用旧单条均值承诺日容量。需要后续正常日运行观测，才能证明跨日稳定性。

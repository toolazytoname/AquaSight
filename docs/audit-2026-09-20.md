## 1. P0-1 采集流水线已停摆 10 天（先修这个）

### 证据

- GitHub Actions `collect.yml` 最后一次**成功的定时运行**是 `2026-09-09 15:15 UTC`（6m27s）。
- 之后的每一次运行（push 触发 + 定时触发）全部 **0 秒失败**，GitHub 标注：`This run likely failed because of a workflow file issue.`
- 线上 `/api/v1/events?view=latest` 最新 `publishedAt` = `2026-09-10T02:08:49Z`；`/api/v1/digest` 返回的早报 `date=2026-09-21` 但 `items=0`。
- 页面顶部显示"更新于 9/21 12:22"——这是**快照写入时间**，不是内容时间，掩盖了内容已陈旧 10 天的事实。

### 根因

`.github/workflows/collect.yml` 第 72~88 行：shell heredoc 里的 Python 代码**顶格写、没有缩进**，直接破坏了 YAML 结构：

```yaml
        run: |
          if [ -n "$INGEST_URL" ] && [ -n "$INGEST_TOKEN" ] && [ -f data/events.json ]; then
            python3 - <<'PY'
import json                    # ← 这一行起全部顶格，YAML 解析直接失败
d = json.load(open("data/events.json"))
...
```

`python3 -c "import yaml; yaml.safe_load(...)"` 报错：`line 74, column 1: could not find expected ':'`。

引入 commit：`88f0bb3 Make Worker ingest survive a full collect snapshot`。

### 修法（给下游模型）

1. 把 heredoc 内的 Python 代码整体缩进到与 `run: |` 块一致（建议缩进 12 空格），或更稳妥地把这段 Python 抽成 `scripts/build-ingest-payload.py` 文件，workflow 里只调 `python3 scripts/build-ingest-payload.py`。
2. 修完后手动 `workflow_dispatch` 跑一次确认恢复。
3. **加"采集失败告警"**：工作流失败时发 Bark/邮件（仓库里已有 Bark 通道），否则下次还会静默死 10 天。
4. **前端加陈旧度提示**：`snapshotAt` 与内容最新 `publishedAt` 相差超过 24h 时，banner 显示"内容可能已陈旧（最新一条为 X 天前）"，不要用快照时间冒充更新时间。

## 2. AI 功能全景：接了什么、断在哪、用户为什么感知不到

### 2.1 系统里实际有两套"翻译/整理"，只有一套是 AI

| 机制 | 文件 | 模型/服务 | 产出 | 现状 |
|------|------|-----------|------|------|
| AI 整理（enrich） | `src/enrich.js` | xAI `grok-4.5`（`XAI_API_KEY`） | `titleZh / overviewZh / facts / impact / evidence / uncertainty / attribution / category` | **线上大面积 fallback，见 2.2** |
| 标题机翻 | `src/translate.js` | **MyMemory 免费翻译 API（不是 AI，不是用户配的模型）**，每次运行预算仅 15 条 | `titleZh / summaryZh` | 在跑，但覆盖极少 |

> 用户以为"我加入了 AI"，但标题翻译走的是 MyMemory 免费接口；grok 只负责 enrich。两者产出字段还互相覆盖（`enrichItems` 里 `next.titleZh = en.titleZh`），调试时很难分清一条中文标题是谁翻的。**建议改造时统一走 AI，删掉 MyMemory 路径**（或反过来只留机翻，但那就谈不上"AI 产品"）。

### 2.2 AI 为什么没生效：两道闸门把它掐死了

**闸门一：单价未配置 → 直接 fallback。**
`src/enrich.js` 的 `resolvePricing` 要求必须配置 `XAI_USD_PER_MTOK_IN/OUT`（成本控制设计，本身合理）。线上没配 → 每条都返回 `fallbackEnrichment(item, "pricing-missing")`。线上 30 条精选里 **26 条 `enrichInsufficient=true`**。

**闸门二：正文抓取失败 → 模型"资料不足"。**
`extractFeaturedBodies`（`src/pipeline.js`）对每条精选去抓原文正文，8 秒超时。大量海外站点（OpenAI/TechCrunch/BBC…）在 GitHub Actions 网络环境下抓不到 → `body` 为空 → prompt 里只有标题 → 模型诚实地回答 `insufficient=true`（这是 prompt 设计要求的："禁止根据标题虚构细节"，设计本身是对的）。

**结果（线上精选 30 条实测）**：

- `titleZh` 覆盖 15/30（一半是 MyMemory 机翻的功劳）
- `overviewZh` 覆盖 12/30
- `facts` 覆盖 **1/30**
- `impact / evidence / attribution` 基本全空

### 2.3 最伤体验的 bug：把内部错误码渲染给用户看

`fallbackEnrichment` 把失败原因写进 `uncertainty: ["资料不足，未调用或未通过模型校验：pricing-missing"]`，`web/app.js` 详情页把 `uncertainty` 原样渲染成"不确定性"小节。于是用户在详情页看到：

> 不确定性
> • 资料不足，未调用或未通过模型校验：pricing-missing

普通用户看到 `pricing-missing` 完全不知所云。**修法**：`uncertainty` 里机器可读的 reason（`pricing-missing`、`http-500`、`no-credential`）只能进日志/诊断接口，UI 只显示一句人话："这条还没有 AI 整理，稍后会自动补上"（或干脆不显示该小节）。

### 2.4 AI 的"可见性"几乎为零

前端其实**渲染了** AI 产出（`app.js` 的 `cardHtml`/`renderDetail`：中文标题、中文概述、要点、影响、证据、归属都在），但：

- 徽章文案是"已整理/待整理"——不提 AI，用户以为只是编辑状态；
- 顶部小字"中文整理 12/30"——像内部进度条，用户看不懂，也不知道这是 AI 干的；
- AI 真正有价值的结构化产出（要点 facts、影响 impact、多家报道对比）因为 2.2 的原因几乎为空，**巧妇难为无米之炊**；
- 详情页的小节标题（概述/要点/影响/证据/不确定性/归属）是学报式语言，没有"AI 解读"的产品化包装。

**改造方向（详见 §6）**：修好供给（闸门一、二）之后，把 AI 产出做成一等公民：卡片上的"✨ AI 要点"3 条以内、"AI 速读"折叠块、明确的"由 grok-4.5 整理 · 置信度/资料不足"标识。

## 3. 登录体验：既奇怪、又坏着

### 现状

- 唯一登录方式：**邮箱 + 6 位验证码**（`src/auth.js`，OTP 10 分钟有效，60 秒重发间隔）。
- **生产环境 `MAIL_DRIVER=log`**（README 原话："当前 Worker 是 `MAIL_DRIVER=log`，不会发信"）→ 用户点"发送验证码"后 toast 说"已提交。验证码 10 分钟内有效。"，但**信永远不会到**。登录功能事实上不可用。
- 弹窗 UI（见 `docs/audit-shots/desktop-login.png`）：
  - 邮箱框、验证码框、两个长得一模一样的按钮（"发送验证码"/"登录"）**同时全部摊开**，没有分步、没有倒计时、没有"已发送至 xxx@xx.com"的状态反馈；
  - 说明文案"不会告诉别人这个邮箱是否注册过"是给安全工程师看的，普通用户只会觉得莫名其妙；
  - 失败后 toast"验证码无效或已过期"，不区分原因。

### 值得先回答的产品问题

这是个**个人新闻站**。登录带来的唯一增量是"收藏/偏好跨设备同步"。为一个低频功能让首屏顶栏常驻"登录"按钮、并维护一整套 OTP+邮件+限流+会话系统，**投入产出比存疑**。给下游模型两个方案，按主人偏好选：

- **方案 A（推荐，减法）**：默认游客模式（本地存储已实现得不错），把登录入口从顶栏撤到设置页深处；登录方式改为 **magic link**（点邮件里的链接即登录，不用手输 6 位码），或者干脆先做"导出/导入本机数据（JSON）"替代跨设备同步。
- **方案 B（保留 OTP，补齐体验）**：修 `MAIL_DRIVER=resend` 并配 `MAIL_API_KEY`；UI 改两步走（输邮箱→发送→出现验证码框+60s 倒计时+"重新发送"）；`autocomplete="one-time-code"` 已有，加分；文案改成"验证码已发送至 xxx，10 分钟内有效"。

## 4. 信息源盘点：缺口与补强方案

### 4.1 现有 15 个源（`src/pipeline.js` `SOURCES` / `src/catalog.js`）

HN、GitHub（开源发现）、36氪文章、36氪快讯、微博/百度/头条热搜（线索）、IT之家、量子位、V2EX、华尔街见闻、TechCrunch、BBC、The Verge、OpenAI 官方。

**健康状况**：本地快照 `sourceErrors` 显示 qbitai / v2ex / wallstreetcn / techcrunch / bbc / verge / openai **全部 `fetch failed`**（采集机网络被墙/反爬的可能性最大——36氪、HN、GitHub、IT之家、热搜类正常）。等于 15 个源常年只有 8 个在出内容，科技栏半壁江山是哑的。

### 4.2 用户点名要的，现在都没有

| 用户期望 | 现状 | 补强方案（均已验证可行） |
|----------|------|--------------------------|
| **GitHub 热门/趋势** | 现有 `github.js` 是 `stars:>=20 created:>近7天` 的搜索，README 明说"GitHub 不是趋势榜" | ① 抓 `https://github.com/trending`（HTML，无官方 API，需容错+缓存）；② 或用 OSSInsight API（`api.ossinsight.io`，免费，有 trending repos）；③ 保留现有"开源发现"作为第二梯队。新增源 `github-trending`，role 仍归 tech |
| **Hugging Face** | 无 | 已验证两个免 key 端点：`GET https://huggingface.co/api/daily_papers`（每日论文，实测返回 50 条/天）；`GET https://huggingface.co/api/models?sort=likes7d&direction=-1&limit=N`（近 7 日最受喜欢模型，实测可用）。可再加 `spaces`  trending。对"对 AI 感兴趣"的用户这是最对口的源 |
| **Product Hunt** | 无 | 官方 GraphQL API 需 developer token；也可用 TrendingAI 同款思路只取当日 top |
| Hacker News | ✅ 已有（`hn.js`，含评论数/讨论链接，做得不错） | 用户"看不太懂"是因为全英文——这恰恰是 AI 翻译/摘要该出力的地方，修好 §2 就能解决 |

### 4.3 采集健壮性（给下游模型的硬要求）

- 每个源失败要**可观测**：现在有 `sourceHealth`，但没有主动告警。加一条：源连续 N 次失败 → Bark 通知主人。
- 海外源在 GitHub Actions 拉不动时，考虑给 `getText`/`getJson` 加代理出口（`HTTPS_PROXY`）或改用 rsshub/镜像；至少把 BBC 的 RSS 双 endpoint 失败打日志分级。
- 新源接入时同步更新三处：`src/catalog.js`（SOURCE_CATALOG + SOURCE_LABELS）、`web/rules.js`（SOURCE_FILTERS）、README 源清单。现在这三处是手工同步的，漏一处筛选器里就没有新源。

## 5. UI / UE 逐条问题清单

> 对应截图：`docs/audit-shots/`（desktop-featured / mobile-featured / desktop-detail / desktop-login / desktop-settings）。前端是无框架原生 JS SPA：`web/index.html`（135 行）、`web/app.js`（1334 行，字符串拼 HTML）、`web/style.css`（**全站仅 170 行 CSS**）。

### 5.1 首屏与信息流（精选/最新）

1. **信息密度过低**：桌面端主列 `max-width:720px` + 卡片 `padding:24px 0`，一屏只能看到 1.5 条新闻；纯文字无缩略图、无热度/评分可视化（后端明明有 `score/value/scoreParts` 字段，前端一个都没用）。
2. **侧边栏 176px 只放了 4 个无图标文字链接**，大面积留白浪费；导航项无图标、无未读计数。
3. **"更新于 9/21 12:22"是快照时间不是内容时间**（见 P0-1），且用绝对时间 `9/9 01:00`，没有"x 小时前 / 3 天前"的相对时间——新闻产品里相对时间是标配。
4. 卡片 kicker 行（来源+时间+"N 家报道"）全是灰字 12px，层级糊成一片；"已整理/待整理"徽章语义不明（见 §2.4）。
5. **卡片动作按钮（收藏/隐藏）是 12px 灰字无图标**，像脚注不像按钮；没有"稍后读/分享"（分享只在详情页有）。
6. 筛选区："来源"折叠面板 + "只看未读" + 主题 pill 混在一起；移动端把搜索框挤到第二行，首屏只剩标题+一条新闻。
7. 空状态文案还可以，但"暂时没有新闻，稍后刷新再看看"在采集停摆时会永远挂着——结合 P0-1 的陈旧度提示一起修。

### 5.2 详情页

8. **把内部错误码 `pricing-missing` 渲染给用户**（P0-3，见 §2.3）。
9. 小节标题"概述/要点/影响/证据/不确定性/归属"是数据字段名直译，不是产品语言；且多数小节为空时不该渲染标题（现在空小节直接不出现，OK，但"不确定性"反而把机器原因露出来了）。
10. "原文摘录 / 尚未生成中文概述，不会根据标题编造。"——诚实是美德，但作为主文案反复出现等于不断提醒用户"我们的 AI 没干活"。应降级为灰字小注，主区域给出"查看原文"CTA。
11. 无相关推荐、无上下篇导航，看完即死胡同。

### 5.3 登录/设置弹窗

12. 登录弹窗问题见 §3（布局、文案、倒计时、MAGIC LINK 方案）。
13. **设置页信息架构混乱**：外观 / 屏蔽来源（否定式"不想看的来源"）/ 保存设置 / "导入一条链接"（一个内容生产功能藏在设置里）/ 口味校准入口 / 本机数据清理，全堆在一个 480px 弹窗里。"导入链接"应该上主导航或"+ 号"入口。
14. "屏蔽来源"是 checkbox 黑名单，用户更想要的是**订阅式白名单**（默认全开、逐个点亮感兴趣的主题/源），AI 产品惯例是正向选择。
15. 弹窗用 `inert` + backdrop blur 做得规规矩矩（无障碍是亮点，保留），但移动端弹窗内滚动和底部安全区要回归测一遍。

### 5.4 全局

16. **视觉系统过于单薄**：全站 170 行 CSS、单一浅绿主色、无卡片阴影层次、无图标系统（纯文字按钮）、无骨架屏（加载中就一句"加载中…"）。不是"极简"，是"没设计"。
17. `toast` 2.4 秒消失且不可操作（"收藏待同步"这种应该带"重试"）。
18. PWA/深色模式/无障碍/`/` 快捷键/undo 隐藏这些**底层功夫其实做得不错**——问题集中在视觉层和信息设计层，改造时别推倒重来，保留这些。

## 6. 竞品与设计参考（不要闭门造车）

### 6.1 TrendingAI（用户点名，已调研）

- 仓库 `github.com/HarlonWang/TrendingAI`，站点 `trendingai.cn`（Kotlin Multiplatform + Material 3，Android/iOS/Web）。
- 信息架构值得直接借鉴：**今日精选（AI 每日从全网筛）→ GitHub 热门 → HN 热议 → Product Hunt 新品**，按源分区，每条带 **AI 智能摘要**（"每个项目自动生成 AI 分析"）+ **历史回溯**（查看任意日期的榜单）+ 每日邮件订阅。
- 对照差距：鸭先知的"精选"是打分排序，没有"每日 AI 精选"的仪式感；没有按源分区浏览；没有历史回看（数据里其实有 `archive.json` 和 firstSeenAt，做历史页成本很低）。

### 6.2 TrendRadar（`github.com/sansan0/TrendRadar`）

热榜聚合 + 关键词过滤 + **AI 分析板块**（趋势概述、热度走势、情感倾向）。借鉴点：把 AI 放在"板块级洞察"而不只是"单条翻译"——鸭先知可以在早报顶部加一段"今日 AI 综述"（3~5 句，由 grok 对当日精选生成），这是让用户**一眼感到 AI 存在**的最便宜手段。

### 6.3 通用设计模式（AI 新闻/聚合类产品惯例）

- **AI 内容要有品牌化的视觉锤**：固定图标（✨）、固定位置（标题下第一块）、固定文案（"AI 速读"），并附"内容由 AI 生成，可能有误"的克制免责——比现在"已整理"徽章强得多。
- **相对时间 + 来源 favicon + 热度指示**（HN 的 score/评论数、GitHub 的 stars 增长）是科技信息流的三件套，目前全缺。
- **早报页当 Newsletter 设计**：日期导航、分栏（科技/商业/世界）、可分享链接——现在早报只是"items 列表"。
- 参考 Particle.news 的"多来源聚合一条新闻"展开方式：鸭先知数据结构里 `sources/memberIds` 已支持"N 家报道"，UI 上只显示了一行小字，可以做成详情页的核心卖点（同一事件不同媒体怎么讲）。

# AI 实际使用与额度复核

## 当前接入

AI 用于候选文章的中文标题、概述、最多三条事实、影响分析、实体与分类、归属与不确定性，以及每日早报综述。采集、初始聚类去重、初始打分与配额选稿仍是规则；搜索也是文本匹配。没有多轮追踪事件变化、跨报道矛盾核验或个性化语义推荐。

早报综述仅把标题传给模型，在通知之后生成，通知模板不含综述。上次 Agnes 中文测试稿经过会话内编辑并由手动工作流推送，尚非每日自动编辑流程。

## 线上证据

- 2026-09-25 采集运行 `36134683260`，代码 `86fcac4`，耗时 54 分 19 秒；环境为 `MODEL_DAILY_CANDIDATE_CAP=0`。
- 最新精选 API 30 条：ready 2、insufficient 3、failed 11、queued 12、状态缺失 2；15 条有中文 titleZh，3 条有非空 facts。中文标题可能直接来自中文原文，不能等同于 AI 成功。
- 上述运行日志中的输出记录：46 次 `invalid:not-object`、1 次 `invalid:bad-category`、23 次旧 `BUDGET_CANDIDATES`。这是事件结果统计，不是本轮 HTTP 请求数。
- `enrichOne` 在缓存命中时直接返回；pipeline 将降级结果也存入缓存。这会复用旧失败，取消上限后也不自动重试。
- 成功缓存的 key 仅包含版本和内容，不含模型/接口。后续切换模型也需要处理缓存版本。
- Worker 公共状态仍报 candidate-cap，但新版采集快照为 blockedReason=null、dailyCandidateCap=0；旧 Worker 状态逻辑仍套用旧上限，不能据其判断最新采集被拦住。

## 用量与容量

13:17:45Z 发布的 events.json budget：day=2026-09-25、dayCandidates=199、calls=703（累计）、daySpent=0、monthSpent≈12.1193 CNY、输入单价 0.05 USD/百万 token、输出单价 0.2 USD/百万 token、dailyCandidateCap=0。金额是应用记账，不是服务商账单；当天记为零不证明没有消耗。

按该配置单价，假设每次输入 2000 token、输出 1800 token：100–400 次/天估计约 0.33–1.32 元/天，约 10–40 元/30 天，不含额外重试或其他任务。400 次每天全部额外重试一次约 2.65 元/天、79.49 元/30 天。这是规划假设，非实测消耗，且不代表 Agnes 或 Littlellm 实际报价。

免费服务商的每日 token/请求额度、当前余额尚未拿到，不能用本地 100 元预算推算。公开页面没有提供可核实的该账户配额。

## Agnes 实测

使用本机已配置 `agnes-2.0-flash` 与真实文章标题/摘要，沿用项目 buildPrompt：

- max_tokens=600 返回 HTTP 200，但 finish_reason=length；600 个输出 token 中 303 为 reasoning、297 为正文，JSON 无法解析。
- 紧接着 max_tokens=1800 请求返回 HTTP 429，没有限额响应头。不能仅凭 429 判定每日额度已耗尽。
- 间隔后再试仍为 429；错误正文明确为免费用户达到 API rate limit，并提示 Token Plan。未给出限流时间窗口、重置时间或剩余额度，不能认定是日额度耗尽，也不能据此承诺全天可用。

## 优先修复方向

1. 区分成功缓存与失败记录，失败带重试时间，切换模型使相应缓存失效。
2. 标题翻译与完整分析分开；为结构化输出留够 token，记录 finish_reason；限流退避、超时与有界重试。
3. 每日先保证早报与精选的中文覆盖、事实可追溯和质量，再扩大处理范围。
4. 把早报编辑接到正式发布前，并让网页、通知使用同一版内容。
5. 按提供商和任务记录请求数、输入/输出/推理 token、成功率、429、延迟；修正线上状态页面，再依据一整天数据判断余量。

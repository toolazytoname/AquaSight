# 鸭先知整条信息流质量检查（2026-09-25）

## 每天会运行多少

配置为每天四轮采集（北京时间 03:00、09:00、15:00、21:00），一轮早报（08:05），每小时一次只读停更检查，以及每天一次只读精选质量检查。早报默认至多一条通知；突发通知默认关闭，异常报警条件触发。GitHub Actions 的 `schedule` 是触发配置，不是送达保证：今天早报工作流实际于 12:23 北京时间启动（原定 08:05），运行约半分钟。今天 15:00 的采集任务实际于 20:23 北京时间启动，运行约 54 分钟。这些延迟比模型写稿本身更影响“早报”体验，应优先解决调度和发布时效。

Free 的应用内每日候选硬上限已关闭。本轮调整后每次采集最多尝试整理 40 条高优先级候选，每天名义至多 160 个候选；早报最多选 10 条并生成一次综述。缓存、候选重合、失败重试会让实际请求数变化，不应把候选数当成免费服务商的调用额度。突发通知与失败报警不需要 AI。

## 线上基线与优先顺序

在今天新一轮 Free 采集发布前，线上精选 30 条中只有 2 条 `aiState=ready`，14 条标题仍为英文，3 条有事实要点；10 条已超过 48 小时。17 个采集源状态均报告正常，因此主要问题发生在排序、模型整理、任务时效和发布环节，而非大面积源故障。旧版质量脚本把“本来就中文的标题”错算为未中文化；已修正并把英文标题、占位标题、AI 完成率加入每天质量门禁。

1. **P0：发布时效和精选新鲜度。** 今日把有时间记录的精选限定在 48 小时内；下一步需把采集与早报从会延迟数小时的 GitHub 定时调度中解耦，并以实际 `snapshotAt`/完成时间验收。只移动 cron 时间无法保证准时。
2. **P0：优先处理可见内容。** 今天已把每轮 AI 候选调整为按早报、精选、分数排序后的前 40 条，避免长尾处理把本轮发布拖到下一轮。正文抓取也改为最多四路并行，按原候选顺序交给 AI。进一步发现文件存储在导入每篇文章、事件与成员关系时重复读取和重写完整状态，已有状态压缩后约 7 MB；现在这些相邻写入合并为带锁的一次原子保存。
3. **P1：内容质量和溯源。** 模型对结构化输出仍偶有占位模板、解析失败和过长综述；校验、重试已加强。接下来按来源级别检查原文时间、链接可用性、事实是否真正可在来源中定位，再决定是否允许推送。
4. **P1：状态持久化。** 采集进度、去重与预算主要依赖 GitHub Actions cache；缓存丢失可能造成重复处理或用量统计回退。应迁移到现有持久化存储，再评估高频采集。
5. **P2：Free 子路由。** New API 有 `free`、`free:fast`、`free:smart`，分别接入 FreeLLMAPI 的 `auto`、`auto:fast`、`auto:smart`。内部排序权重不同，但今天对同一材料试 `fast`、`smart` 时两者都由 `dots-studio/dots-3-note-preview:free` 承接，耗时约 3 秒且均未完成 JSON。仅凭名称不能判定 smart 更好；目前应用继续使用外层 LiteLLM 的 `free`，不把尚未证明有收益的子路由用于生产。
